Moving a large POS test suite from Katalon to Playwright

How to move a large POS suite without a freeze, keeping both suites running until the new one earns trust.

Sudhanshu ShekharSenior QA Automation Engineer · 3 min read · October 2026

At iVend Retail I moved our POS and ERP regression tests from Katalon Studio to Playwright with JavaScript. That was more than 400 scenarios. Writing the new tests was not the hard part. The hard part was keeping releases safe while the move was going on.

These are the things that worked for me.

1. Keep the old suite running

The biggest risk in a migration is a gap: the old tests are switched off and the new ones are not ready yet. Releases don't wait for you to finish.

So we ran both suites side by side. Katalon kept checking every release, and the Playwright suite grew next to it. I only removed a scenario from Katalon after its Playwright version had passed reliably for several runs. Being written was not enough. It had to prove itself first.

2. Build the common parts first

It's tempting to start converting tests on day one, because the progress is easy to show. I started with the shared pieces instead, because all 400 tests would use them:

  • Login, done once and shared, not repeated in every test
  • POS actions like adding items, discounts and payment, as page objects
  • API calls for creating test data and checking results
  • Test data helpers, so each test creates only what it needs
  • Logging, so a failure in CI tells you what happened

Playwright fixtures made this simple. A test asks for what it needs, like a logged-in POS page, and the fixture does the setup and the cleanup.

3. Rewrite the test, don't copy it

If you copy a Katalon test line by line, you get a Playwright test with the same old problems: fixed waits, long setup through the screens, and checks on whatever text happened to be visible.

So I rewrote each scenario. The biggest change was the setup. Many old tests logged in and created their data through the UI before they even got to the part being tested. I moved that to the API: log in once and share the session, and create data directly. That one change made the suite about 30% faster.

// Before: every test logs in through the UI
await page.goto('/login');
await page.fill('#email', user);  // ...and so on

// After: log in once, reuse the saved session in every test
// playwright.config.js
use: { storageState: '.auth/cashier.json' }

4. Start with what matters most

I didn't go folder by folder. I started with the flows where a bug costs the business the most: sign-in, sales, pricing, GST, discounts, stock and payment. Those got good coverage in the new suite first.

5. Make CI flexible, and fix flaky tests properly

The suite runs in GitHub Actions. For each run you can choose the suite, the environment and the browser. A developer can run a quick check on one module, and a release gets the full regression, which takes about 50 minutes.

The hardest problems were tests that failed only in CI. On my machine they passed every time. The causes turned out to be:

  • cookies and sessions behaving differently in CI
  • Docker environment settings
  • timing differences between browsers

The easy way out is to add retries. I didn't do that. Retries hide problems, and you can't sign off a release with a suite that "usually passes". Finding the real cause takes longer, but that's what made the team trust the results.

If you are planning the same move

  1. Keep the old suite running until the new one has proved itself.
  2. Build the shared parts and fixtures before converting tests.
  3. Rewrite each test, especially the setup. Use the API wherever the UI is not what you are testing.
  4. Start with the flows that cost the most when they break.
  5. Treat a flaky test as a bug to fix, not noise to retry.

A migration is a good chance to get rid of old habits, not just to change tools.
