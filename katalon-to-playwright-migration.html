Migrating 400+ scenarios from Katalon to Playwright

How to move a large POS suite without a freeze, keeping both suites running until the new one earns trust.

SS
Sudhanshu ShekharSenior QA Automation Engineer · 3 min read · October 2026

At iVend Retail I'm moving our POS and ERP regression suite from Katalon Studio to Playwright (JavaScript). So far that's more than 400 scenarios. The hardest part of a migration like this isn't writing the new tests. It's making sure the product stays protected the whole time you're doing it.

Here's how I approached it, and what I'd tell anyone planning the same move.

Rule 1: never stop the old suite

The biggest risk in a test migration is a gap: a period where the old suite is switched off and the new one isn't ready. Releases don't pause for your migration.

So both suites kept running side by side. Katalon kept guarding every release, and Playwright grew next to it. A scenario was only retired from Katalon once its Playwright version had run reliably over multiple cycles and caught the same things. The new suite had to earn trust before it took over.

Run old and new in parallel. Retire a test only when its replacement has proven itself, not when it's merely written.

Rule 2: build the foundation before migrating tests

It's tempting to start converting tests on day one, because it shows visible progress. I started with the shared building blocks instead, because every one of the 400 tests would depend on them:

  • Login, done once and shared, not repeated in every test
  • POS actions like adding items, applying discounts and taking payment, as page objects
  • An API client for creating test data and checking results on the server
  • Test data helpers, so each test creates exactly what it needs
  • Logging, so a failure in CI explains itself

Playwright fixtures made this clean. A test asks for what it needs, such as a logged-in POS page or an API client, and the fixture handles setup and cleanup.

Rule 3: migrate, don't translate

A line-by-line translation of a Katalon test gives you a Playwright test with all the old problems. Recorded tests often carry habits like fixed waits, long UI-driven setup and assertions on whatever text was visible.

So each scenario was redesigned, not copied. The biggest change was setup. Many old tests logged in and created data through the UI before they even reached the thing being tested. I replaced that with API calls: log in once through the API and share the session state, and create test data directly. That one change cut suite runtime by about 30%.

// Before: every test logs in through the UI
await page.goto('/login');
await page.fill('#email', user);  // ...and so on

// After: log in once via API, reuse the session everywhere
// playwright.config.js
use: { storageState: '.auth/cashier.json' }

Rule 4: migrate by risk, not by folder

I didn't migrate in the order tests happened to sit in the Katalon project. I started with the flows where a bug costs the business most: sign-in, sales, pricing, GST, discounts, stock and payment. Those got the strongest coverage in the new suite first, so the riskiest areas were the first to benefit from faster, more reliable tests.

Rule 5: make CI flexible and fix failures at the root

The suite runs in GitHub Actions, with options to pick the suite, the environment and the browser for each run. That means a developer can run a quick check on one module, while a release gets the full regression. The full regression suite completes in about 50 minutes.

The hardest bugs were failures that only happened in CI. They passed on my machine every time. The causes turned out to be things like:

  • cookie and session handling that behaved differently in the CI environment
  • Docker environment configuration
  • browser-specific timing differences

The easy fix is to add retries and move on. I avoided that. Retries hide problems, and a suite that "usually passes" can't be used to sign off a release. Fixing each root cause is slower, but it's what made the suite stable enough that the team trusts its results.

What I'd tell someone starting this

  1. Keep the old suite running until the new one has earned its place.
  2. Build shared components and fixtures before converting tests.
  3. Redesign each test, especially its setup. Use the API wherever the UI isn't the thing being tested.
  4. Start with the flows that cost the most when they break.
  5. Treat flaky tests as bugs to fix, not noise to retry.

A migration is a chance to fix years of habits, not just change tools. Done carefully, you end up with a suite that's faster, cleaner and, most importantly, trusted.
