Why my tests check the server, not the screen

Verifying invoices, GST and stock through the API catches the bugs a UI-only assertion misses.

SS
Sudhanshu ShekharSenior QA Automation Engineer · 4 min read · October 2026

Most UI tests end by checking something on the screen: a success message, a total, a receipt. If it looks right, the test passes. In retail POS testing, I've learned that this isn't enough. The screen shows what the frontend thinks happened. What matters is what the server actually booked.

The screen can be right while the data is wrong

A POS screen can show a correct total and still save a wrong invoice. Some of the ways this happens:

  • The frontend calculates tax one way, and the server recalculates it differently when the invoice is saved.
  • A discount looks applied on screen, but isn't saved with the invoice.
  • The receipt prints, but the invoice is stuck as a draft instead of paid.
  • The sale completes, but stock isn't deducted, or the invoice isn't linked to the right customer or payment.

Each of these passes a UI-only test. Each of them is a real problem for a retailer: wrong tax filings, wrong stock counts, or money that doesn't reconcile at the end of the day.

The pattern: set up with the API, act in the UI, check the server

My tests follow one simple pattern:

  1. Set up through the seed or the API. Items, prices, GST and tills are created directly. The setup screens aren't what's being tested, so there's no reason to click through them.
  2. Act through the UI. Do what a cashier does: add items, check out, take payment. This is the behaviour under test.
  3. Check the server. Read back the record the sale created, by its name, and check what was saved.

Here's part of a real test from my ERPNext POS framework, TC-POS-001: a cashier sells one item for cash.

const stockBefore = await api.stockQty(item.code, testData.warehouse)

// Act: the sale, through the POS screen
await pos.addItem(item)
await pos.checkout()
await pos.payWith('Cash', String(price.gross))
const sale = await pos.completeOrder()

// Check: the invoice this sale booked, read back by its name
const invoice = await api.getDoc('Sales Invoice', sale.name)
expect(invoice).toMatchObject({
  is_pos: 1,
  docstatus: 1,            // submitted, not a draft
  net_total: price.net,
  grand_total: price.gross,
  pos_profile: till.name,
})
expect(taxOn(invoice, testData.gst.cgstAccount)).toBe(price.halfGst)
expect(taxOn(invoice, testData.gst.sgstAccount)).toBe(price.halfGst)
expect(paidRows(invoice)).toEqual([{ mode: 'Cash', amount: price.gross }])

// Stock: exactly one fewer, and this invoice booked the -1
expect(await api.stockQty(item.code, testData.warehouse)).toBe(stockBefore - 1)

The key detail is that the test takes the invoice name from the screen's own response and reads that invoice. It never searches for "the latest invoice", which could belong to another test.

What I check on the server

For a POS sale, the test case lists exact values for the saved Sales Invoice:

  • Status: it's a POS invoice and it's submitted, not left as a draft.
  • Money: net ₹100.00, CGST ₹9.00, SGST ₹9.00 and grand total ₹118.00 for an item sold at ₹118 with 18% GST included.
  • Payment: one payment row, Cash ₹118.00. For UPI or card sales, the transaction ID or card details are saved too.
  • Links: the right customer, cashier and till.
  • Stock: exactly one lower, and the stock movement booked by that invoice is −1.

At work, the same idea covers pricing, discounts, stock deduction and payment flows. If a sale should reduce stock, the test checks the stock level, not a message saying "sale complete".

A bonus: faster, more stable tests

Moving setup to the API wasn't only about better checks. It made the whole suite faster and less flaky. At iVend Retail, replacing UI-driven login and data creation with API calls cut suite runtime by about 30%. Fewer clicks means fewer places for timing issues, and each test spends its time on the behaviour that matters.

When the screen still matters

This doesn't mean UI checks are useless, and my own framework taught me that the hard way. At one point I checked every total through the API only. But the POS screen applied a default tax template that the API didn't, so the POS added an extra 6% tax (₹100.00 became ₹106.00) while every API check said ₹100.00. The server checks were green; a real customer would have been overcharged.

So TC-POS-001 checks both: the cart must show Net Total ₹100.00, CGST ₹9.00, SGST ₹9.00 and Grand Total ₹118.00, and the saved invoice must have the same values. A good test confirms that the two agree.

The screen is what the user sees. The server is what the business keeps. Test both, and make sure they agree.

Try it on your own suite

Pick one end-to-end test that ends with a UI check. Add one API call at the end that fetches the record it created and checks a few key fields. There's a good chance you'll find something the screen was hiding.
