Why my tests check the server, not the screen

Verifying invoices, GST and stock through the API catches the bugs a UI-only assertion misses.

SS
Sudhanshu ShekharSenior QA Automation Engineer · 3 min read · October 2026

Most UI tests end by checking something on the screen: a success message, a total, a receipt. If it looks right, the test passes. In retail POS testing, I've learned that this isn't enough. The screen shows what the frontend thinks happened. What matters is what the server actually booked.

The screen can be right while the data is wrong

A POS screen can show a correct total and still save a wrong invoice. Some of the ways this happens:

  • The frontend calculates tax one way, and the server recalculates it differently when the invoice is saved.
  • A discount looks applied on screen, but isn't saved with the invoice.
  • The receipt prints, but the invoice is stuck as a draft instead of paid.
  • The sale completes, but stock isn't deducted, or the invoice isn't linked to the right customer or payment.

Each of these passes a UI-only test. Each of them is a real problem for a retailer: wrong tax filings, wrong stock counts, or money that doesn't reconcile at the end of the day.

The pattern: arrange with the API, act in the UI, assert on the server

My tests follow one simple pattern:

  1. Arrange through the API. Create the item, price and tax setup directly. The UI isn't what's being tested here, so there's no reason to click through it.
  2. Act through the UI. Do the thing a cashier does: add items, apply a discount, take payment. This is the behaviour under test.
  3. Assert on the server. Fetch the booked invoice through the API and check what was saved.
test('POS sale books correct GST on the server', async ({ posPage, api }) => {
  // Arrange: set up data through the API
  const item = await api.createItem({ rate: 1000, taxTemplate: 'GST 18%' });

  // Act: complete the sale like a cashier would
  await posPage.addToCart(item.code, 2);
  const invoiceName = await posPage.payWithCash();

  // Assert: check what the server actually booked
  const invoice = await api.getInvoice(invoiceName);
  expect(invoice.status).toBe('Paid');
  expect(invoice.total_taxes_and_charges).toBe(360);
  expect(invoice.grand_total).toBe(2360);
});

The key detail is that the test reads the invoice by name, the exact invoice this sale created. It doesn't search for "the latest invoice", which could belong to another test running in parallel.

What I check on the server

In my ERPNext POS framework, the API client checks each booked invoice for three things:

  • Status: the invoice is actually paid and submitted, not left as a draft.
  • GST totals: tax is calculated on the right amount, after discounts, and matches the tax template.
  • Links: the invoice points to the right customer, items and payment.

At work, the same idea extends to stock deduction, pricing and payment flows. If a sale should reduce stock by two, the test checks the stock level, not a message saying "sale complete".

A bonus: faster, more stable tests

Moving setup to the API wasn't only about better checks. It made the whole suite faster and less flaky. At iVend Retail, replacing UI-driven login and data creation with API calls cut suite runtime by about 30%. Fewer clicks means fewer places for timing issues, and each test spends its time on the behaviour that matters.

When the screen still matters

This doesn't mean UI assertions are useless. The cashier needs to see the right total, the right error message when stock runs out, and a receipt that matches the invoice. So I check both: the screen for what the user sees, and the server for what the business keeps. A good test confirms that the two agree.

The screen is what the user sees. The server is what the business keeps. Test both, and make sure they agree.

Try it on your own suite

Pick one end-to-end test that ends with a UI check. Add one API call at the end that fetches the record it created and checks a few key fields. There's a good chance you'll find something the screen was hiding.
