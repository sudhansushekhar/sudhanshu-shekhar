Why my tests check the server, not the screen

Verifying invoices, GST and stock through the API catches the bugs a UI-only assertion misses.

Sudhanshu ShekharSenior QA Automation Engineer · 3 min read · October 2026

Most UI tests end by checking something on the screen: a success message, a total, a receipt. If it looks right, the test passes. In POS testing I learned that this is not enough. The screen shows what the frontend thinks happened. What really matters is what the server saved.

The screen can be right while the data is wrong

A POS screen can show the correct total and still save a wrong invoice. For example:

  • The screen calculates tax one way, and the server calculates it differently when it saves the invoice.
  • A discount shows on screen but is not saved with the invoice.
  • The receipt prints, but the invoice is still a draft, not paid.
  • The sale goes through, but stock is not reduced, or the invoice is linked to the wrong customer.

A test that only looks at the screen passes in all of these cases. For a shop, each one is a real problem: wrong tax, wrong stock, or cash that doesn't match at the end of the day.

How I write these tests

I follow the same three steps every time:

  1. Set up through the API. Items, prices, GST and tills are created directly. I'm not testing those setup screens, so there's no reason to click through them.
  2. Do the action in the UI. Do what a cashier does: add items, check out, take payment. This is the part being tested.
  3. Check the server. Read back the record the sale created, by its name, and check what was saved.

Here is part of a real test from my ERPNext POS framework, TC-POS-001, where a cashier sells one item for cash:

const stockBefore = await api.stockQty(item.code, testData.warehouse)

// The sale, on the POS screen
await pos.addItem(item)
await pos.checkout()
await pos.payWith('Cash', String(price.gross))
const sale = await pos.completeOrder()

// Read back the invoice this sale created, by its name
const invoice = await api.getDoc('Sales Invoice', sale.name)
expect(invoice).toMatchObject({
  is_pos: 1,
  docstatus: 1,            // submitted, not a draft
  net_total: price.net,
  grand_total: price.gross,
  pos_profile: till.name,
})
expect(taxOn(invoice, testData.gst.cgstAccount)).toBe(price.halfGst)
expect(taxOn(invoice, testData.gst.sgstAccount)).toBe(price.halfGst)
expect(paidRows(invoice)).toEqual([{ mode: 'Cash', amount: price.gross }])

// Stock went down by exactly one
expect(await api.stockQty(item.code, testData.warehouse)).toBe(stockBefore - 1)

One detail matters a lot here. The test takes the invoice name from the screen's own response and reads that exact invoice. It never searches for "the latest invoice", because that could belong to another test running at the same time.

What I check on the saved invoice

For a ₹118 item with 18% GST included, the test case lists the exact values:

  • Status: it is a POS invoice and it is submitted, not a draft.
  • Amounts: net ₹100.00, CGST ₹9.00, SGST ₹9.00, grand total ₹118.00.
  • Payment: one payment row, Cash ₹118.00. For UPI or card sales, the transaction ID or card details are saved too.
  • Links: the right customer, cashier and till.
  • Stock: exactly one less, and the stock entry made by this invoice is −1.

At work I use the same idea for pricing, discounts, stock and payments. If a sale should reduce stock, the test checks the stock number, not a "sale complete" message.

A side benefit: faster tests

Doing the setup through the API also made the tests faster and less flaky. At iVend Retail, moving login and data creation from the UI to API calls cut the suite runtime by about 30%. Fewer clicks means fewer timing problems.

The screen still matters

I don't skip UI checks, and my own project showed me why. At one point I checked every total through the API only. But the POS screen was adding a default tax template that the API did not. The screen added an extra 6% tax, so ₹100.00 became ₹106.00, while every API check still said ₹100.00. All my server checks were green, and a real customer would have paid too much.

So now TC-POS-001 checks both. The cart must show Net Total ₹100.00, CGST ₹9.00, SGST ₹9.00 and Grand Total ₹118.00, and the saved invoice must have the same values. The test makes sure the screen and the server agree.

Try it on one of your tests

Pick one end-to-end test that ends with a UI check. Add one API call at the end that reads the record it created and checks a few fields. You might be surprised by what turns up.
