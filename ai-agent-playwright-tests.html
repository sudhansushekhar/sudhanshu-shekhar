Letting an AI agent write Playwright tests, safely

Lint rules, edit hooks and mutation checks that keep AI-written tests traceable to requirements and able to fail.

Sudhanshu ShekharSenior QA Automation Engineer · 5 min read · October 2026

I use Claude Code to write Playwright tests in my ERPNext POS project. It is fast. But early on I noticed a problem. Many of the tests it wrote would pass even if the feature was broken. A test like that is worse than no test, because it makes you feel safe when you are not.

So I set up some rules. Most of them are checked by scripts, so I don't have to catch everything by reading each line. In this post I'll go through them one by one.

What went wrong at first

I keep a file called ai-review-log.md. Every time the AI gets something wrong, I write it down there. A few real examples:

  • It wrote the login test from memory. It looked for a "Login" button and expected the Desk at /app. ERPNext v16 has a "Continue" button and opens /desk.
  • To prove a test could fail, it changed toBeVisible() to toBeHidden(). The test still passed, because the dialog had not loaded yet. So the "proof" proved nothing.
  • It used the no-restricted-imports lint rule to block some imports. My project uses require(), and that rule only looks at import. It never caught anything.

These are normal mistakes. A new tester could make them too. The difference is that the AI can make them many times in one afternoon.

Rule 1: the test case comes first

The AI does not decide what to test. First there is a test case in plain English. Either I write it, or the AI drafts it from the requirement and I review it before anything else happens. Each test case has an ID, the requirement it covers, priority, severity, steps and checks. This is a real one, a bit shortened:

## TC-POS-001 a cashier sells one item for cash: GST included, booked as a POS sales invoice
**Requirement:** REQ-POS-004, REQ-POS-008, REQ-POS-009, REQ-POS-015 · **Priority:** P0 · **Severity:** blocker
**Runs:** `@smoke` · **Test data:** QA-STOCK-001 (₹118.00, GST 18%), Walk-in Customer, Till 1

**Steps**
1. Add 1 × QA-STOCK-001 to the cart.
2. Checkout. Pay ₹118.00 by **Cash**. Complete Order.

**Checks**
- The cart shows Net Total ₹100.00, CGST ₹9.00, SGST ₹9.00, Grand Total ₹118.00.
- The Sales Invoice the screen submitted, read back by name: `is_pos` 1, submitted,
  net ₹100.00, CGST ₹9.00, SGST ₹9.00, grand total ₹118.00, one payment row Cash ₹118.00.
- Stock of QA-STOCK-001 is exactly 1 lower after the sale.

The test title in the code has to be exactly this heading. That way any failure points straight back to a test case and a requirement. The AI is also not allowed to invent a value that is not in the test case. If it needs one, it has to ask me.

Rule 2: lint checks the easy rules

My rules for writing tests are in a file called CLAUDE.md. Some of them are simple enough for a machine to check, so I put those in ESLint:

  • no locators in spec files, they belong in page objects
  • test and expect come only from src/fixtures
  • no waitForTimeout
  • no .only, .skip, .fixme or .fail, and no forced clicks

Every error message says which rule number was broken, so the AI knows what to fix:

{
  selector: `CallExpression[callee.property.name=/^(${LOCATOR_METHODS})$/]`,
  message: 'Rule 4: no locators in specs. Add a method or property to a page object in src/pages.',
}

After the no-restricted-imports mistake, I added one more habit. Before I trust a new lint rule, I run it on a file that breaks it on purpose. If it doesn't complain, the rule doesn't work.

Rule 3: a hook runs after every edit

Running lint only at the end is too late. By then the AI may have written five more files with the same problem. Claude Code supports hooks, so I added one that runs every time the AI edits or writes a file:

// .claude/settings.json
"PostToolUse": [{
  "matcher": "Edit|Write",
  "hooks": [{ "type": "command",
    "command": "node \"$CLAUDE_PROJECT_DIR/scripts/lint-edited-file.js\"" }]
}]

If the file is in tests/ or src/ and lint fails, the script exits with code 2. Claude Code passes the error back to the AI, and it has to fix the file before it moves on. The same lint also runs in CI on every pull request.

Rule 4: every test must be able to fail

For me this is the most important one. For every new test, the AI runs /mutation-check:

  1. Pick the main check, for example the grand total.
  2. Change the expected value to something wrong, like 118 to 119.
  3. Run the test. It has to fail.
  4. Put the value back and run it again. It has to pass.

If the test still passes with the wrong value, it isn't testing anything, and it goes back to be fixed. From the toBeHidden() mistake I also learned that for visibility checks you should change the situation, not the assertion. For example, open the till first, so the opening dialog should not show up at all.

Rule 5: every mistake turns into a rule

Each entry in the review log has three parts: what the AI did, why it was wrong, and what I changed so it doesn't happen again. After the login button mistake, the rule became "read the real page before writing locators". Another time a WebKit test passed using 60 of its 60 seconds, then failed on the next run. Now the rule is to look at how long each test takes, not just whether it passed.

What I still do myself

  • approve the test cases, and add the negative cases the AI missed
  • review every test against my 10-point checklist
  • decide when code is pushed. The AI asks, I say yes or no.

To sum up

The AI writes code much faster than I do. But its goal is a passing test, not finding bugs. So I give it the same rules I'd give a new person on the team, and I put those rules into scripts so they get checked every single time. Everything in this post is in the repo if you want to look at the real files.
