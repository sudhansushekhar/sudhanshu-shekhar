Letting an AI agent write Playwright tests, safely

Lint rules, edit hooks and mutation checks that keep AI-written tests traceable to requirements and able to fail.

SS
Sudhanshu ShekharSenior QA Automation Engineer · 6 min read · October 2026

AI coding agents can write a Playwright test in seconds. That speed is real, and I use it. But speed isn't the hard part of test automation. Trust is. A test suite is only useful if a green run means the product works, and an AI agent left to itself is very good at writing tests that go green for the wrong reasons.

In my open-source ERPNext POS test framework, Claude Code writes the tests, but only inside a set of guardrails. This article walks through them, with the real files from the repo.

What goes wrong without guardrails

I log every mistake the AI makes in docs/ai-review-log.md. A few real entries show the pattern:

  • Writing from memory, not from the product. It expected a "Login" button and the Desk at /app. ERPNext v16 shows "Continue" and lands on /desk. The AI was writing from older versions.
  • A check that couldn't fail. To prove a test worked, it flipped toBeVisible() to toBeHidden(). The test still passed, because the dialog hadn't been drawn yet. The "proof" proved nothing.
  • A guardrail that guarded nothing. It used the no-restricted-imports lint rule to keep page objects out of specs. That rule only sees ES import, and the repo uses require(), so it caught nothing.

None of these are unusual; a junior tester could make any of them. The difference is that an agent can make them many times in an afternoon. So every rule that a program can check, a program checks.

The loop: the AI writes, the tester decides

Every test goes through the same steps. The AI does the fast work; I do the judging.

  1. A requirement goes into docs/requirements/ with an ID, like REQ-POS-004.
  2. The AI drafts test cases from it (/test-cases), marked Status: draft.
  3. I review the draft, fix values, add missing cases and set Status: approved.
  4. The AI writes the test from the approved case (/write-test), runs it and mutation-checks it.
  5. The AI and I review the test against a 10-point checklist (/review-test).
  6. What the AI got wrong goes into the review log, and a new rule goes into CLAUDE.md.

Guardrail 1: every test starts from an approved test case

The AI doesn't decide what to test. A test case in plain English comes first, in a fixed format: an ID, the requirement it checks, priority, severity, steps and checks. Here is a real one, shortened:

## TC-POS-001 a cashier sells one item for cash: GST included, booked as a POS sales invoice
**Requirement:** REQ-POS-004, REQ-POS-008, REQ-POS-009, REQ-POS-015 · **Priority:** P0 · **Severity:** blocker
**Runs:** `@smoke` · **Test data:** QA-STOCK-001 (₹118.00, GST 18%), Walk-in Customer, Till 1

**Steps**
1. Add 1 × QA-STOCK-001 to the cart.
2. Checkout. Pay ₹118.00 by **Cash**. Complete Order.

**Checks**
- The cart shows Net Total ₹100.00, CGST ₹9.00, SGST ₹9.00, Grand Total ₹118.00.
- The Sales Invoice the screen submitted, read back by name: `is_pos` 1, submitted,
  net ₹100.00, CGST ₹9.00, SGST ₹9.00, grand total ₹118.00, one payment row Cash ₹118.00.
- Stock of QA-STOCK-001 is exactly 1 lower after the sale.

**Change it when** the POS payment screen, GST setup, POS profile or stock settings change.

Two rules make this work. The test's title must be the test case's exact heading, so every failure traces back to a case and a requirement. And the AI must not invent a value the test case doesn't give. If it needs one, it asks.

Guardrail 2: a lint that enforces the rules

CLAUDE.md lists the rules for writing tests. The ones a machine can check are in eslint.config.js, and each error message names the rule number it breaks:

  • specs import test and expect only from src/fixtures; page objects and the API come as fixtures
  • no locators in specs; they live in page objects
  • no waitForTimeout: wait for the server, not the clock
  • no .only, .skip, .fixme or .fail, and no forced clicks
{
  selector: `CallExpression[callee.property.name=/^(${LOCATOR_METHODS})$/]`,
  message: 'Rule 4: no locators in specs. Add a method or property to a page object in src/pages.',
}

After the no-restricted-imports mistake, there's one more rule about the rules: every lint rule is proven on a deliberately bad example before it's trusted. A lint rule that never fires is the same as a test that never fails.

Guardrail 3: a hook lints every file the AI edits

Linting at the end isn't enough, because by then the agent may have built several files on top of a bad pattern. Claude Code supports hooks, so after every file the AI edits, a hook lints that file:

// .claude/settings.json
"PostToolUse": [{
  "matcher": "Edit|Write",
  "hooks": [{ "type": "command",
    "command": "node \"$CLAUDE_PROJECT_DIR/scripts/lint-edited-file.js\"" }]
}]

If the edited file is under tests/ or src/ and breaks a rule, the script exits with code 2 and prints the lint output. Claude Code hands that straight back to the agent, which has to fix it before going on. The same lint runs for people with npm run lint, and in CI on every pull request.

Guardrail 4: a mutation check proves each test can fail

This is the guardrail I value most. A test that can't fail is worse than no test, because it gives false confidence. So every new test goes through /mutation-check:

  1. Pick the assertion that guards the main business result, such as the grand total.
  2. Change only its expected value to something wrong but plausible, like 118 → 119.
  3. Run the test and show it fails.
  4. Restore the value exactly, run again and show it passes.

If the test still passes after the change, it proves nothing and gets reworked. The toBeHidden() mistake added a lesson here: for a visibility check, break the state (for example, open the till first so the dialog must not appear), not the direction of the assertion.

A green test only means something if you've seen it go red for the right reason.

Guardrail 5: every AI mistake becomes a rule

The review log isn't a list of complaints. Each entry records what the AI did, why it was wrong, and the rule or fix added so it doesn't happen again. "Locators come from the real page's accessibility tree, read before writing" came from the Login-button mistake. "Read test durations, not only pass/fail" came from a WebKit test that passed at 60 of its 60 seconds, then failed on the next run.

The agent forgets instructions. The rules in CLAUDE.md, the lint and the hook don't.

What I still do by hand

The guardrails don't replace a tester. They free up time for the parts that need judgement:

  • approving test cases: the right values, the missing unhappy paths, the questions the AI should have asked
  • reviewing each test against the checklist, especially "checks the saved record, not only the screen"
  • approving the rules that come out of the review log
  • deciding when code is pushed: the AI asks, I decide

The takeaway

AI agents are fast, but they aim for a passing test, not a meaningful one. The answer isn't to avoid them. It's to give them the same rules a good QA team gives a new hire: start from approved test cases, follow the coding standards, get every change checked, prove every test can catch a bug, and learn from every mistake. Put those rules in code, and the agent follows them every time.
