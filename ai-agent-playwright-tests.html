Letting an AI agent write Playwright tests, safely

Lint rules, edit hooks and mutation checks that keep AI-written tests traceable to requirements and able to fail.

SS
Sudhanshu ShekharSenior QA Automation Engineer · 4 min read · October 2026

AI coding agents can write a Playwright test in seconds. That speed is real, and I use it. But speed is not the problem in test automation. Trust is. A test suite is only useful if a green run actually means the product works, and an AI agent left to itself is very good at producing tests that go green for the wrong reasons.

In my open-source ERPNext POS test framework, I let Claude Code write tests, but only inside a set of guardrails. This article explains what those guardrails are and why each one exists.

What goes wrong without guardrails

When I first let an agent write tests freely, the same problems kept appearing:

  • Invented scope. The agent tested what it saw on the screen, not what the product was supposed to do. If the UI had a bug, the agent happily wrote a test that confirmed the bug.
  • Weak assertions. A test would check that a "Success" message appeared and stop there. The invoice behind that message was never checked.
  • Flaky shortcuts. Hard waits like waitForTimeout(3000), forced clicks and raw selectors scattered through test files.
  • Quiet weakening. When a test failed, the easiest fix for the agent was sometimes to loosen the assertion until it passed.

None of these are unusual. Junior testers make the same mistakes. The difference is that an agent can make them fifty times in an afternoon. So I built rules that catch them automatically.

Guardrail 1: tests only come from approved test cases

The agent is not allowed to decide what to test. Every test starts from a plain-English test case that a human has written and approved, and every case is traced to a requirement ID from the PRD.

# cases/pos-sale.md (approved)
REQ-POS-04  Sell one taxable item and pay by cash
  Given an item with an 18% GST tax template
  When the cashier sells 2 units and pays by cash
  Then the invoice is booked as Paid
  And GST and grand total match the tax template

The agent's job is translation: turn this case into a Playwright test. The test title must carry the requirement ID, so anyone can trace a failure back to the requirement it protects. If a case doesn't exist, the agent can't write the test. Deciding what is worth testing stays with me.

Guardrail 2: lint rules reject bad patterns

ESLint runs on every test file. Some rules come from eslint-plugin-playwright; others are custom rules written for this project.

// eslint.config.js (simplified)
rules: {
  'playwright/no-wait-for-timeout': 'error',  // no hard waits
  'playwright/no-force-option': 'error',     // no forced clicks
  'playwright/expect-expect': 'error',       // every test must assert
  'playwright/no-skipped-test': 'error',
  // custom: test title must include a requirement ID
  // custom: no raw selectors outside page objects
}

Lint rules are cheap, fast and impossible to argue with. A human reviewer gets tired by the twentieth file. A lint rule does not.

Guardrail 3: an edit hook checks every change

Linting at the end isn't enough, because by then the agent may have built ten files on top of a bad pattern. Claude Code supports hooks: scripts that run automatically when the agent edits a file. My hook runs the checks on each edit and rejects changes that break the rules, such as:

  • editing the approved test case files (the agent may read them, never change them)
  • adding a hard wait or a forced click
  • a test without a requirement ID

When the hook rejects an edit, the agent sees the error message and has to fix its own work before moving on. The feedback loop is immediate, the same way a good reviewer would comment on a pull request, just much faster.

Guardrail 4: a mutation check proves each test can fail

This is the guardrail I value most. A test that cannot fail is worse than no test, because it gives false confidence. So every new test has to prove it can go red.

The idea comes from mutation testing: deliberately change something the test depends on, and confirm the test notices. For example, change the expected GST amount, or point the check at a different invoice. If the test still passes after the mutation, it isn't really checking anything, and it gets rejected.

A green test only means something if you have seen it go red for the right reason.

What I still do by hand

The guardrails don't replace a tester. They free up my time for the parts that need judgement:

  • deciding what is risky and worth testing, and writing the approved cases
  • reviewing the agent's code like any other pull request
  • investigating failures, especially ones that only happen in CI
  • exploratory testing, which no agent does well yet

The takeaway

AI agents are fast, but they optimise for a passing test, not a meaningful one. The answer isn't to avoid them. It's to give them the same rules a good QA team gives a new hire: work from requirements, follow the coding standards, get every change reviewed, and prove your test can catch a bug. Put those rules in code, and the agent follows them every time.
