About

From mechanical engineering to test automation, with a focus on reliable regression suites.

I'm a QA Automation Engineer with 5+ years of experience testing retail POS and ERP systems. At iVend Retail I'm leading the move of our POS automation from Katalon to Playwright (JavaScript).

I build frameworks that verify what the server actually booked — invoice status, GST totals, stock — rather than trusting the UI alone. My suites run in GitHub Actions with selectable suites, environments and browsers, and I dig into CI-only failures until they're fixed at the root, so the regression suite is stable enough for release sign-off.

I have a B.Tech in Mechanical Engineering and moved into software testing in 2021. Since then I have worked across retail, telecom, HR scheduling and ERP products. Lately I've been exploring how AI coding agents can write tests safely, with lint rules and review guardrails keeping them honest.

ERPNext POS Test Framework

A Playwright (JavaScript) framework for ERPNext Retail POS India, built to show how I design a suite end to end.

  • 11 end-to-end tests (sign-in and POS sale), 3 page objects, 3 fixture layers and a REST API client that checks each booked invoice by name: status, GST totals and links.
  • GitHub Actions spins up ERPNext in Docker, seeds data through the API and checks the site is ready. Pull requests run @smoke on Chromium; nightly runs cover every test on Chromium and WebKit.
  • Guardrails let an AI coding agent write tests safely: tests come only from approved plain-English cases traced to PRD requirement IDs, lint rules and an edit hook reject bad patterns, and a mutation check proves each test can fail.

How to play: this shop receipt has 5 hidden mistakes. Tap any line you think is wrong. A red mark means you found a bug; a green flash means that line is correct. Each bug you find unlocks its explanation.

Receipt paper stock after sale−2 left

GST 18% (on ₹2,205.00)₹441.00
Total₹2,511.90

0 of 5 found

Start by tapping any line on the receipt.

  • Line total ignores quantity: 3 × ₹150 should be ₹450.00
  • Stock went negative; the sale should be blocked or flagged
  • Discount is added instead of subtracted
  • GST calculated on pre-discount amount; 18% of ₹2,205 is ₹396.90
  • Total doesn't add up: ₹2,205 + ₹396.90 = ₹2,601.90

A real bug my automated test TC-POS-005 caught in the Retail POS India app, written up the way I report bugs at work. It was fixed the same day.

Title
Tapping Cash on the payment screen turns it off, so the number pad types nothing
Found by
Automated test TC-POS-005 (number pad), nightly run
Requirement
REQ-POS-010: the cashier types the amount on the number pad
Severity
Major P2. The cashier cannot enter a cash amount until they tap Cash a second time.
Environment
ERPNext v16 with Retail POS India, local Docker. Chromium and WebKit. Cashier Anjali Verma on Till 1.
Steps
  1. Add 1 × QA-STOCK-001 to the cart.
  2. Click Checkout. Cash is already selected.
  3. Tap Cash.
  4. Type 5 0 0 on the number pad.
Expected
Cash shows ₹500.00.
Actual
Cash gets unselected and the number pad does nothing. The amount does not change.
Cause
ERPNext's payment tiles work like an on/off switch. Tapping the tile that is already selected switches it off.
Fix
The app now keeps a tapped tile selected and starts a new amount (pull request #1).
Retest
TC-POS-005 passes on Chromium and WebKit. Status: closed.

A real test case from my ERPNext POS framework. Every test case is written in plain English first; the automated test's title is its exact heading.

TC-POS-001 a cashier sells one item for cash: GST included, booked as a POS sales invoice

Requirement REQ-POS-004, 008, 009, 015 Priority P0 Severity blocker Runs @smoke

Test data: QA-STOCK-001 (₹118.00, GST 18%, stock in Stores - QAR), Walk-in Customer, Till 1

Steps
  1. Add 1 × QA-STOCK-001 to the cart.
  2. Checkout. Pay ₹118.00 by Cash. Complete Order.
Checks
  • The cart shows Net Total ₹100.00, CGST ₹9.00, SGST ₹9.00, Grand Total ₹118.00.
  • The Sales Invoice the screen submitted, read back by name: is_pos 1, submitted, customer Walk-in Customer, net ₹100.00, CGST ₹9.00, SGST ₹9.00, grand total ₹118.00, one payment row Cash ₹118.00, POS profile Till 1.
  • Stock of QA-STOCK-001 in Stores - QAR is exactly 1 lower, and the stock movement booked by that invoice is −1.

Change it when the POS payment screen, GST setup, POS profile or stock settings change.

The automated test for TC-POS-001 (shortened), from tests/pos/sale.spec.js. The sale happens on the screen; the checks read back what the server booked.

const { test, expect, meta } = require('../../src/fixtures')

test('TC-POS-001 a cashier sells one item for cash: GST included, booked as a POS sales invoice',
  { tag: ['@smoke'] }, async ({ pos, till, api, testData }) => {
  meta({ priority: 'P0', severity: 'blocker', feature: 'POS', story: 'REQ-POS-004' })
  const item = testData.items.stock
  const price = gstSplit(item)
  const stockBefore = await api.stockQty(item.code, testData.warehouse)

  // The screen: cart totals
  await pos.addItem(item)
  expect(await pos.totals()).toMatchObject({
    'Net Total': rupees(price.net), CGST: rupees(price.halfGst),
    SGST: rupees(price.halfGst), 'Grand Total': rupees(price.gross),
  })
  await pos.checkout()
  await pos.payWith('Cash', String(price.gross))
  const sale = await pos.completeOrder()

  // The server: the invoice this sale booked, read back by its name
  const invoice = await api.getDoc('Sales Invoice', sale.name)
  expect(invoice).toMatchObject({ is_pos: 1, docstatus: 1, grand_total: price.gross })
  expect(paidRows(invoice)).toEqual([{ mode: 'Cash', amount: price.gross }])
  expect(await api.stockQty(item.code, testData.warehouse)).toBe(stockBefore - 1)
})
